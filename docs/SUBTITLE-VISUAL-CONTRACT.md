# 字幕视觉契约

烧录字幕长什么样，由这一份契约定义。它同时管两条交付路径：

| 交付     | 渲染器                          | 内容                   |
| -------- | ------------------------------- | ---------------------- |
| 单语中文 | `render-subtitles.py`           | 一行中文               |
| 中英双语 | `render-bilingual-subtitles.py` | 中文在上，英文原文在下 |

**机器可读的唯一事实来源是 `packages/adapters-node/src/acquire/subtitle_style.py`。**
本文解释为什么是这些值；改样式改那个文件，本文跟着更新。契约测试
（`subtitle-style-python.test.ts` 及两个渲染器的 `*-python.test.ts`）会把下表锁住。

> 本契约取代 `docs/BILINGUAL-SUBTITLE-BURN-TASK.md` v0.3 里的视觉部分（亮黄中文、
> 斜体英文、ASS 烧录）。那份文档已归档，不再作为样式依据。

## 视觉规格

### 中文

| 项目 | 值                                  |
| ---- | ----------------------------------- |
| 字体 | 思源黑体 Heavy / Noto Sans SC Black |
| 字重 | 900                                 |
| 字号 | 30px（720p 基准，按分辨率缩放）     |
| 颜色 | `#FFFFFF`                           |
| 描边 | 1px 纯黑（发丝线，3×3 膨胀）        |
| 阴影 | `0 4px 20px rgba(0,0,0,.5)`         |
| 字距 | 0                                   |

**单语中文和双语里的中文行是同一样东西** —— 单语交付就是双语去掉英文行，不是它的放大版。同一条 cue 经两个渲染器出来的字身逐像素相同，`subtitle-style-python.test.ts` 里有一条测试直接比对两边渲染结果来钉住这一点。

### 英文

| 项目 | 值                 |
| ---- | ------------------ |
| 字体 | Inter Bold         |
| 颜色 | `#FFFFFF`          |
| `AI` | `#FFD928`          |
| 描边 | 1px 纯黑（发丝线） |
| 阴影 | 见下「英文阴影」   |
| 字距 | `0.02em`           |

### 两行共用

| 项目       | 值                         |
| ---------- | -------------------------- |
| 行距       | `1.65em`（按各行自身字号） |
| 水平安全区 | 画幅宽度 80%               |
| 背景框     | 无                         |

## 需要解释的几处

**没有背景框。** 可读性由描边和阴影承担。代价是白字压近白画面时对比度明显低于底框方案 —— 这是规格选定的取舍。1px 发丝描边就是为这种场景保的底：规格只写了阴影，但纯阴影在白底上撑不住。

**阴影是绝对像素，不是字号比例。** 规格写的就是 CSS 绝对值，按 720p 绝对像素记录、只随分辨率缩放，两条路径在同一分辨率下拿到同一个阴影。（这条在单语还有自适应字号时更要紧：按字号比例算会让相邻字幕的阴影粗细跳变。字号统一后这个风险没了，但绝对像素仍是对规格更忠实的记法。）

**CSS 的 blur 要折半再交给 Pillow。** CSS `blur-radius` 是 2σ，Pillow `GaussianBlur` 的 radius 就是 σ。规格的 20px 进 Pillow 是 10。直接传 20 会让扩散翻倍。

**描边是固定像素，不随字号缩放。** 发丝线是恒定的视觉重量。早先按 8% 字号算会在各分辨率下变成 2-4px，明显过重。

**描边的画法本身也是契约。** 用的是字形的 3×3 偏移膨胀，**不是** Pillow 的 `stroke_width`（后者用 FreeType 描真实轮廓）。同样标称 1px，两种画法出来差一两个像素 —— 所以这是外观的一部分，不是实现细节，两个渲染器必须用同一个 `draw_outlined_runs()`。

**居中用 `(画幅宽 - round(advance)) // 2`，不用 Pillow 的 `ms` 锚点。** 后者按浮点 advance 居中，两者在某些行上差 1px —— 同一条 cue 由两条路径渲染时看得出来。

**换行按 advance 宽度判断，不按墨迹 bbox。** 墨迹 bbox 窄了两侧边距，同一句话会断在不同的字上。

**行距 1.65em 是重新定的。** 两条路径原来分别是 ~1.50em（双语：在字体自身行高上加固定 2px，两行几乎粘连，上一行的投影糊到下一行）和 2.00em（单语：额外加 0.55em，两行散成两块）。1.65em 是实际读起来像一条两行字幕的值。

**`AI` 用 `\bAI\b` 匹配，只作用于英文行。** `AI`、`AI-generated` 命中；`AIs`、`SAIL`、`Thai` 不命中。中文行和所有阴影图层都传 `highlight_re=None` —— 高亮词的投影和其余部分同色，不会投出一个黄色阴影。

**英文阴影沿用旧值**（`距离 0.08 / 模糊 0.1 / 45° / #404040 42%`，按字号比例）。规格定义了英文的字体、颜色和字距，没有提阴影；而这一行没有描边，阴影是白字与画面之间唯一的分隔。它按字号比例是合理的：它所属的双语行每个分辨率只有一个固定字号。

**字重 900 拿不到时会告警。** 思源黑体是 17MB 的 CJK 字形，不适合进仓库，靠宿主机发现。找不到就回退 PingFang / Hiragino，字重明显更轻 —— 这时 stderr 会打 `WARNING`，不让它冒充设计原样。Inter 只有 420KB，已 vendored 进 `src/acquire/fonts/`，仓库副本为准。

## 排版机制（不属于视觉契约）

这些留在各渲染器内部，因为两条路径解决的是不同问题：

**英文字号。** 双语英文行固定 16px（720p 基准）。中文字号属于视觉契约（见上），英文没有需要对齐的对手，所以留在渲染器内部。

**长句切分。** 由上游 `projectSemanticBilingualSubtitles` 完成，不在渲染器：16 个 CJK 触发切分、14 是每段目标、20 是硬上限、最多 2 行，按标点缝切并避开受保护术语。切分要重新分配时间轴，渲染器做不到这件事。`full.zh.srt` 和 `full.bilingual.srt` 出自同一次调用，所以两条路径拿到的是同一批已切好的 cue。渲染器只负责排它拿到的东西：放不下就换行，**绝不缩小字号**。

**画布尺寸。** 两条路径都把每个 cue 渲染到**同一个**全宽固定高度的画布上。ffmpeg 的 image2 输入一旦遇到尺寸变化就会重建滤镜图，会扰动整条 overlay 链 —— 这正是双语渲染器当初被改成固定行高的原因，单语后来也对齐了。

**底部锚定。** `burn-subtitles.ts` 用 `overlay=...:H-h-margin` 把 PNG 的**底边**钉在画面上。所以布局从行底往上排，让**最后一条基线**落在恒定位置：换行的 cue 向上生长。按降部底边锚定是不行的 —— 换行的 cue 会选更小字号、降部更浅，于是整条往下掉几个像素。

## 验证

```bash
pnpm test packages/adapters-node/src/acquire
```

烧录后的抽帧验收走 `verify-subtitles.py`，比对烧录帧与原帧在底部区域的像素差异。去掉背景框后信号来自字形、描边和大范围柔和阴影 —— 在暗、中、亮、复杂亮 UI 四种背景下实测均为满分。改动阴影或描边时要重跑这个验收，别只看单帧截图。
