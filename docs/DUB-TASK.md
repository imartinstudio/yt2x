# 双语字幕 + 中文配音：架构方案

> 本文取代 2026-07-30 版《中文配音任务设计》。旧版把配音设计成一条独立交付路径，并在
> 决策 #5 / #8 中锁定「只烧中文字幕」「只出配音版」——这两条框定错误导致配音自建了一套
> 与双语字幕并行的交付链路，是此后大量缺陷的共同来源。本文重新定义交付物。

## 交付物

**一个视频**：原片画面 + 中文配音音轨（保留 BGM）+ 中英双语硬字幕，字幕与配音语音精确对齐。

配音是**双语字幕交付的一个可选增强**，不是独立产物。关掉配音时走现有双语字幕交付；打开时
把音轨换成中文、字幕跟着配音时间轴重计时，**只烧一次**。

## 核心取舍（已确认）

中文比英文普遍长 10–30%，三者不可兼得：

|                | 取舍                                       |
| -------------- | ------------------------------------------ |
| ① 锁死原片时长 | **选定**                                   |
| ② 语速自然均衡 | 保留，靠前置吸收让它极少被触发             |
| ③ 译文信息完整 | 在翻译阶段以「凝练」形式让步，而非事后砍削 |

选 ① 的理由：素材是讲者出镜与录屏交替的混合形态，冻结画面在出镜段落非常明显；而全程
1.2 倍以上语速在长视频上疲劳感强。

**关键**：③ 的让步做对了几乎无损。英文口语冗余度高（填充词、同义反复、换个说法再说一遍），
带时长预算翻译时这些先被挤掉，实质内容基本不动。当前实现测得的 44% 信息损失，是「先自由
翻译再让 LLM 事后砍」的顺序错误造成的，不是这个取舍的固有代价。

## 时长吸收的四层顺序

必须按序吸收，前层做对则极少走到后层：

1. **长度受限翻译** —— 翻译时即带「本句可用 N 毫秒」预算，挤掉口语冗余
2. **利用原片句间静音** —— 说话人换气的空档是现成余量
3. **轻微调速 0.95–1.15** —— 吸收残余，听感无损
4. **压缩内容** —— 兜底，前三层做对后应极少触发

当前实现跳过了第 1、2 层，直接从第 4 层开始，这是质量问题的根源。

## 两级切分

解决「字幕要短」与「分句要自然」的表面矛盾：

```
话语单元 utterance   ← TTS 合成单位；来自源语音的换气停顿，不是字幕行
        ↓ 合成后得到该句的实测起止
显示单元 cue         ← 在话语单元内部按屏宽再切，时间按字符比例分配
```

因为显示单元是话语单元的**细分**，而话语单元的实际时长是**实测值**，四项要求同时成立：
字幕短、分句自然、不漂移（误差不跨句累积）、中英同源同时间轴。

## 数据流

```
原片（downloads，只读）
  ├─ 音轨 ─→ ASR 词级时间戳（faster-whisper，已有）
  │            ↓
  │        话语切分（按停顿聚类）          ← 新增
  │            ↓
  │        长度受限翻译（带时长预算）       ← 新增，取代事后压缩
  │            ↓
  │        TTS 合成（带时间戳，已有）
  │            ↓
  │        时长吸收（静音 + 调速，改造）
  │            ↓
  │        中文音轨 + 时间轴映射 T→T′
  │
  └─ 人声分离（Demucs，已有）─→ BGM 轨
                ↓
        混音（中文人声 + BGM）
                ↓
  双语字幕按 T′ 重计时（中文=配音稿，英文=同话语单元原文）
                ↓
        换音轨 + 烧一次 → 成片
```

**配音不再自己烧片。** 它交出音轨与时间轴映射，由双语交付路径统一烧录。

## 落地顺序

分四个 PR，每个可独立验收：

1. **话语切分** —— 从词级时间戳产出话语单元；纯函数 + 单测；不改动现有链路
2. **长度受限翻译** —— 新 prompt + 预算参数；与旧路径并存以便对比
3. **切换链路** —— 配音改为消费话语单元；废弃 `segment.ts` / `shorten-prompts.ts`
4. **统一交付** —— 配音退出烧录，双语路径按 T′ 重计时并烧一次

前两个 PR 不影响现有行为，可安全先行。

### PR4 的完整范围

除「统一交付」本身外，PR3 交付后试听真实成片暴露的三项也一并在 PR4 处理——它们都要动同一批时间轴与交付代码，拆开做会重复改：

1. **双语硬字幕**（本就是 PR4 的核心）。PR3 的成片是中文单语，验收标准第四维度「画面上实际出现的是双语」因此**尚未结清**，必须由 PR4 抽帧目视双语来关闭。
2. **句间停顿过长**——第一个手段（反向放慢 `stretch`）**已完成**（PR4 第一批，commit `7dbf9c2`）。实测 148 个间隔：中位 402ms 尚可，但平均 942ms、p90 2930ms、p95 3348ms、最大 4413ms，**33% 超过 1 秒、18% 超过 2 秒**。成因是结构性的——「锁死原片时长」让每句中文从原句起点开始念，而译文普遍短于预算（中位占用 93%，部分行不足 50%），念完剩下的就是死寂。改前**协商只会加速、不会减速**：中文太长时压进去，中文太短时无人处理。已新增 `stretch` 动作，在 slot 有富余时反向放慢（rate 区间 0.95–1.15 的下半段现在会被用到）；上面这段分布是**改前**的历史记录，不代表当前行为。这一项不在原方案的四层吸收顺序里——第 2 层「利用原片句间静音」解决的是溢出，与此相反。

   **第二个手段——拆分过长的话语单元，`maxDurationMs` 默认值下调**——**已完成**（PR4 第二批）。用户试听真实成片后反馈「说完之后长时间静默」，并提出把长句拆成短句。真实全片按原句槽位分组的中文填充率印证了这个判断：槽位越长，念完剩下的死寂越多（0–4s 填充 96%、4–8s 91%、8–12s 81%、12s+ 只有 67%）——`stretch` 只能部分回填，槽位本身太长时译文预算按比例给出，念完就没词了。`segmentUtterances` 原本只在 ASR 整段不给标点时才用 `maxDurationMs`（默认 12000ms）当保险丝在最宽换气点硬切；这一批把它的角色扩展为**主动控制槽位落进填充甜区**的手段——调小它，长句在词间最宽停顿处被提前切开，每段各自拿到自己的时长预算。

   真实全片（807.7s、111 句起点）三组阈值实测（`minDurationMs` 恒为 3000）：

   | maxDurationMs      | 话语单元数 | 总静默    | 静默占比  | 译文总字数 | 门禁                            |
   | ------------------ | ---------- | --------- | --------- | ---------- | ------------------------------- |
   | 12000（旧默认）    | 111        | 116.5s    | 14.4%     | 2685       | passed，0 issue                 |
   | **8000（新默认）** | 121        | **86.6s** | **10.7%** | 2863       | passed，1 advisory（info-loss） |
   | 6000               | 131        | 112.2s    | 13.9%     | 2587       | passed，0 issue                 |

   8000 是总静默最低的一组，且译文总字数不降反升——切分让每句各自拿到更宽松的时长预算，凝练空间更松，不是「取舍」而是双赢。6000 切得更碎（131 句）但总静默反而比 8000 高：每次切分都让新单元重新支付一次中文 TTS 的固定合成开销（约 1873ms），单元数从 121 涨到 131 后，多付的固定开销超过了单句静默缩短的收益。三点已勾出明显的单峰分布，未继续在 8000 附近细调。

   **发现并修复了 `maxDurationMs`（切分阈值）与 `minDurationMs`（合并下限，PR4 第一批引入）的参数冲突**：切分阈值调低后，长句拆出的收尾碎片经常短于 `minDurationMs`，若合并时仍用同一个（已调低的）阈值当上限，碎片常常两边都并不进去——真实数据显示 `maxDurationMs=6000` 时若合并沿用同一阈值，175 个话语单元里有 40 个（23%）卡在原地、短于 3000ms 下限，等于让上一轮刚根治的单字译文问题重新出现。修法是把合并上限与切分阈值解耦（固定在 12000ms，独立于调用方传入的切分阈值），分开后 0 个漏网。新默认值下真实全片复查：**≤2 字译文行数 0/121**，与上一轮的根治结果一致。

3. **默认音色改为 `zh-CN-YunjianNeural`（云健）**——**已完成**（PR4 第一批，commit `c121f8d`）。旧默认 `zh-CN-YunxiNeural`（云希）的引擎标签是 `Novel / Lively, Sunshine`，年轻明亮，与技术讲解的调性不符。已用同一段真实台词横向试听四个中文音色后选定云健——引擎标签 `Sports, Novel / Passion`，实际听感比标签更沉稳；`YunyangNeural`（`News / Professional`）播音腔偏正式，`YunxiaNeural`（`Cartoon / Cute`）不适用。

   **换音色必须重新标定门禁阈值。** 同一段台词实测时长：云希 12.8s、云扬 12.3s、**云健 13.3s**、云夏 14.1s。云健比现行默认**慢约 4%**，方向上是双刃：
   - 对上面第 2 项（停顿过长）**有利**——语音填满更多 slot，死寂变少；
   - 对溢出**不利**——更多行会需要加速或延后。当前 `overflowFraction 0.369`（阈值 0.75）、`medianRatio 0.935`（阈值 1.35）都有余量，4% 不至于击穿，但这两个数连同 `advisoryTextBudgetRetainFraction` 都是按云希标定的，换默认值后必须以云健重跑真实正片重新标定。

## 验收标准（四维度，缺一不可）

此前多次出现「测试全绿而成片是坏的」，原因是每次只测了一个维度：

| 维度     | 判据                                               |
| -------- | -------------------------------------------------- |
| 起点     | 每条显示单元的起点与其语音起点偏差在容差内         |
| 终点     | 语音未被截断；时间戳推出的结束点不超过音频实际时长 |
| 停顿     | 相邻话语单元之间保留非零间隔                       |
| 字幕内容 | **画面上实际出现的是双语**，且中文与听到的一致     |

第四条必须**抽帧目视确认**。此前「字幕文件逐行精确但压根没被烧进画面」的缺陷，任何只校验
文件的断言都发现不了。

**单测全绿不构成验收通过**：必须用 30 秒窗口跑真实素材并按四维度实测，最终由人耳确认听感。

## ElevenLabs 决策（2026-07-31）

**不接入。TTS 只走 edge-tts。**

原方案把「ElevenLabs 时间戳能力未经真实调用验证」列为未决项。该验证必须打真实 API——
现有 `elevenlabs.test.ts` 全是 mock，正因如此才不构成验证。但本项目无 ElevenLabs 账号且
暂不付费，验证无法进行，故这条未决项**关闭为「不做」**，不再继续挂着。

连带结论：

- `dub/elevenlabs.ts` 维持失败关闭，不再计划启用。其 mock 单测只保证代码不腐化，不代表能力可用。
- **音色克隆不做**。克隆能力依赖 ElevenLabs，edge-tts 无此能力，因此该需求随本决策一并关闭。
- `TtsPort` 的多引擎抽象保留。`rateRange`、`speechTiming` 等设计本身是对的，日后若接入付费
  引擎可直接复用，无需推倒重来。

重新开启此决策的条件：有了 ElevenLabs 账号，且完成一次真实调用验证其词/短语级时间戳能填满
`TtsSpeechTiming`（当前 `elevenlabs.ts` 的返回值里根本没有 `speechTiming`）。

- 最小句间停顿默认值（当前 150ms）需在新链路上重新试听确定
- **门禁阈值只在一支真实素材上标定过**。当前值（`advisoryMedianRatio 1.2`、
  `advisoryOverflowFraction 0.5`、`maxDelayFraction 0.35`、`advisoryTextBudgetRetainFraction 0.7`）
  来自 zh-CN-YunjianNeural 的一次全片实跑，样本量不足以支撑更紧。收紧 hard 阈值尤其危险——
  曾因「拿单次样本收紧 `maxDelayFraction`」被打回，实测按收紧后的值，对同一支已通过全片
  门禁的视频做 2 分钟窗试跑会有约 9% 的起点被误拦。
- **换音色必须同时重标定两处**：字符预算的时长模型（`TTS_FIXED_OVERHEAD_MS` /
  `TTS_MS_PER_CHINESE_CHAR`）**和**门禁阈值。上次换音色只标了后者，云健的每字成本比云希
  高约 53%（不是「慢 4%」），字符预算因此系统性偏松，全片被 `extendMs` 硬门禁拦下。
  代码里已有回归哨兵测试钉住这两个常数，换音色时它会失败并逼你显式更新。
- **"译文回来了却被掏空"没有 hard 兜底**：`advisoryTextBudgetRetainFraction` 衡量译文占用了
  多少时长预算，但分辨不出"挤掉口水话"与"砍掉内容"——填充词密集的发言忠实压缩后占用比
  天然很低，所以它只能是 advisory。同理，配音链路的 `glossary-violation` 也已降为 advisory：
  该检查**可以通过让输出变糟来满足**（逼模型补回专名时，它会把已有的派生词译法顶掉，
  检查放行而译文更错）。一个既阻塞发布、又能被劣化满足的门禁，制造的压力方向是错的。
- **窗口冒烟的产物必须与全片隔离**。已隔离：配音稿、时长报告、协商计划、落点报告、门禁
  报告、逐句音频、人声轨、混音轨、源窗口视频、窗口成片与窗口 SRT、**人声分离结果**。
  最后一项曾被漏掉，后果是先跑 30 秒窗验收、再跑全片时背景音只有 30 秒，而门禁
  `issues: []` 全绿完全看不见——正是本文开头警告的「测试全绿而成片是坏的」。新增中间
  产物时按这张表逐项检查。
- **已 dub 视频跳过 preflight 后，`--dub-engine` 拼错不再报错**：`native-pipeline.ts` 里
  `skipDubPreflight` 为真时跳过 `resolveDubEngine` 校验，而 `native-dub.ts` 的
  `executeNativeDub` 又在解析引擎之前就因 `dubbedPath` 已存在而 early-return 0。于是
  `pipeline --dub --dub-engine elevnlabs`（拼错）对一批已经 dub 过的视频会静默退出码
