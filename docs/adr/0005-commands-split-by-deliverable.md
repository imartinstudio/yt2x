# ADR-0005: 命令按交付物切分，而非按阶段

- **Status**: Accepted
- **Date**: 2026-08-03
- **Deciders**: 项目负责人
- **Tags**: cli, commands, pipeline, acquire, subtitle
- **实现状态**: 决策已定，代码尚未落地

## Context

CLI 的参数规模已经失控：`.option(` 定义共 192 处，`pipeline` 一个命令 53 个参数，
`acquire` 33 个、`dub` 29 个、`subtitle` 23 个。

按参数归属拆开看，`pipeline` 实际上同时是**两个产品的入口**：

| 归属                                | 参数数 |
| ----------------------------------- | ------ |
| 共享（源 / 阶段模式 / 输出 / LLM）  | ~16    |
| 视频侧（下载 / 切片 / 字幕 / 配音） | ~22    |
| 图文侧（文章 / 平台改写 / 解构）    | ~12    |

两侧唯一的共同点是从同一个 YouTube 视频取材，但失败模式完全不同：视频侧失败是环境问题
（缺 demucs、缺 TTS 凭据、缺词级时间戳），图文侧失败是 LLM / 网络问题。混在一条 53 参数的
命令里，用户无法预判自己会踩哪一种。

同时，`pipeline` / `acquire` / `subtitle` 三个命令编码的是**阶段**差异，而阶段是实现的缝，
不是用户意图的缝。用户的意图始终是「给我一个交付物」，唯一的变量是「素材下过没有」。为了让
三个入口的同名参数保持一致，代码里额外维护了一层
`packages/cli/src/commands/single-stage-projection.ts` 做投影——这层的存在本身就是征兆。

对该仓库使用者 shell 历史的统计（2026-05-04 至 2026-08-02，696 次调用）显示，实际使用集中
在两个复制粘贴的长命令模板上，各自 11~14 个参数，其中 4 个参数恒定传入与默认值相同的值。

## Decision

### 1. 按交付物切分顶层命令

- `yt2x video`：下载 → 转录 → 字幕 → 配音 → 成片。
- `yt2x text`：笔记 → 长文 → 多平台改写。

命令名对应交付物（一个视频 / 一份文本），不对应阶段。

### 2. `yt2x video` 吸收 `acquire` 与 `subtitle`

「素材下过没有」由输入参数表达，不由命令名表达：

- `--urls <url...>`：从头跑，下载后继续。
- `--video-id <id>`：跳过下载，对已有素材续跑。

`pipeline` / `acquire` / `subtitle` 删除，保留对 `--help` 隐藏的报错桩，指向新写法。
`single-stage-projection.ts` 这层投影随之取消。

### 3. 不设跨侧的组合命令

不提供把 `video` 与 `text` 串起来的第三个入口。全流程是两条命令，由 shell 串接。
`yt2x video` 在收尾打印一条可直接复制的 `yt2x text --video-id <videoId> …`。

### 4. 诊断命令与交付入口分离

`dub`、`dub-replay`、以及原 `subtitle` 下的 `audit` / `repair` / `transcribe-local`
（移入 `subtitle-tools`）保留全部单步参数，但从主 `--help` 折叠，不作为交付入口。

## Consequences

### Positive

- 每条命令能用一句话说清它交付什么，`--help` 可读。
- 「同一个参数在不同入口语义不一致」在结构上消失——每个能力只有一个交付入口。
- 投影层 `single-stage-projection.ts` 及其维护成本取消。
- 两侧的失败模式分离，用户按下回车前就知道自己面对哪一类风险。

### Negative

- 全流程从一条命令变成两条。该仓库使用者的实际工作方式是两侧几乎总是同时要，因此这是每次
  都要付的成本，由收尾打印的可复制命令缓解。
- 现有命令行模板全部失效，需要一次性迁移（`docs/USAGE.md` 提供旧→新对照表）。
- 报错桩是过渡期代码，需要在下次改动命令树时清理。

## Alternatives Considered

### 1. 不切分，只在 `pipeline` 内部重做参数语义

拒绝。改完之后 `pipeline` 仍是 50 个参数，只是每个都更讲道理。切分是本轮唯一能真正减少
单命令参数数量的动作。

### 2. 只在 `--help` 层面分组显示

拒绝。这是化妆：分组后帮助文本更好看，但参数之间的静默否决、双入口双默认一个都没解决，
而且会制造「已经解决了」的错觉。

### 3. 保留一个透传全部参数的组合命令

拒绝。等于把切分的收益退回去，且造出三个入口（`video` / `text` / 组合），比原先两个更糟。

### 4. 组合命令只接受参数的受限子集

拒绝。受限子集必然漂移——两边的取值集合由两处代码分别定义，「同一参数在不同入口不一致」
会原地复活。

### 5. 保留 `subtitle` 作为单阶段命令

拒绝。只要它独立存在，就要有自己的一套交付参数，投影层就得继续维护。「对已取材的视频重出
字幕」用 `yt2x video --video-id <id>` 表达，长度相同，少一个命令名要记。
